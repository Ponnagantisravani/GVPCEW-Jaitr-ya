Automatic Timetable Generation is available to academic coordinators in Timetable Management alongside the existing matrix, upload and conflict options. All four III CSE sections are scheduled together as one global problem.

Setup from the project root (use `npm.cmd` on Windows if PowerShell blocks `npm`):

1. Configure the existing `backend/.env` including DATABASE_URL and existing auth settings.
2. Run `node backend/scripts/migrate-timetable-generator.js`. This creates only the generator's timetable_versions, timetable_slots and timetable_generator_resources tables, indexes and trigger functions. Re-running it refreshes generator triggers. Existing academic tables are untouched.
3. Routes are already mounted under `/api/timetable` in `backend/src/routes/index.js`, after the existing portal router so the old GET `/api/timetable` remains intact. The new router is `timetableGenerator.js`; `routes/timetable.js` already serves the established `/api/timetables` feature and is preserved.
4. The new `TimetableGenerator.jsx` is already connected through the Automatic Generation tab in `TimetableManagement.jsx` for academic coordinators.
5. Start the backend using `npm.cmd --prefix backend run dev` and frontend using `npm.cmd --prefix frontend run dev` in separate terminals.
6. Run `node --test backend/tests/timetableSolver.test.js backend/tests/timetable-generator.test.js`. Optional database checks: `node backend/scripts/test-timetable-generator-db.js` and `node backend/scripts/test-timetable-generator-api.js`. They use isolated schemas inside transactions and roll back all test data. The API test requires an existing active academic coordinator account; it does not create or change accounts.

The primary input is a structured Paste / Type Configuration editor, prefilled with all four sections and the required subject hours. Required room and class-teacher fields are visible immediately, with inline messages and a live list of missing details. Generate Timetable runs validation and faculty allocation automatically; Parse & Validate remains available for reviewing assignments first. It accepts ACADEMIC YEAR, YEAR, DEPARTMENT, SECTION 1–4, ROOM, CLASS TEACHER, subject hours, TEACHER/TEACHERS, and LAB ROOMS. DEVOPS is normalized to DEVOPS LAB. Unknown labels, duplicate/missing subjects, wrong hours and placeholder values produce errors. Each section must contain exactly the specified 36 hours. JSON is also accepted, but CSV is not required.

Enter the real Section 4 room and class teachers for Sections 2–4. No application defaults invent these values. Automated tests use explicit test fixtures for them. Section 1 retains the supplied assignments unless explicitly changed. Empty/Auto assignments use the least-loaded eligible faculty member from the supplied pool; CN/DM labs select two distinct teachers and IRS/MPMC always includes Hemalata plus an IRS faculty member. Counselling and term project use the entered class teacher by default because no separate faculty pools were supplied. All assignments can be overridden in the review table.

Unavailable teacher periods can be entered as `UNAVAILABLE: Dr. D. Indu` followed by lines such as `Monday P2`. Use `ROOM UNAVAILABLE: CSLAB1` for rooms. The constraints editor also supports adding/removing individual unavailable periods and changing lab rooms. Internal slots use day 0–5 and period 1–7, for example `0:2` for Monday P2. Labs reserve every configured room together and never cross lunch.

Honours defaults to one combined III CSE class at P7: HPC Monday/Wednesday/Friday with Dr. SSH, SM Tuesday/Thursday/Saturday with Dr. MBS. It displays in all section grids and is reserved once in faculty/room occupancy, including the five-period teacher daily limit and unavailable slots. Honours days, faculty and optional rooms are editable. Separate honours mode is rejected because the same fixed P7 faculty cannot teach four separate sections simultaneously.

Search uses most-constrained-first backtracking with soft preference scores and bounded random restarts. It runs in a worker thread with at most two concurrent searches per server process. A timeout is reported as an inconclusive search, not proof of impossibility. The API may pass a `solver` object with `nodeLimit`, `timeoutMs` (maximum 60,000) and optional reproducible `seed`; the default search limit is 20 seconds.

Save Draft checks hours, assignments and every hard constraint. Lab occupancy is expanded to three stored period rows, with database triggers maintaining one occupancy row per teacher/room and unique constraints protecting all sections, teachers and rooms. Publish locks the stored version, validates the full timetable again (including expanded lab completeness), and only then marks it published. Published slot rows cannot be edited; save changes as a new draft. Generated versions can be loaded by ID in the UI or retrieved using GET `/api/timetable/:id`.

Section, faculty and room grids derive from the same slots. Labs span three columns, the grid scrolls horizontally, and subject colours have dark-mode variants. Drag/drop requests a full-block swap only after checking constraints; touch/keyboard users can select two entries and use Check & swap. Unsafe swaps preserve the previous valid schedule and report the conflicting resource.

Publishing persists the generated version in the new module. It does not change the existing student/faculty feed or its publication workflow. Connecting those existing tables/pages requires separate authorization and ID mapping. No reference screenshot was available for exact visual comparison. The in-app browser was unavailable during verification; solver tests, database checks and frontend builds provide automated validation. The migration was applied successfully to the configured database after validation. Run it once when setting up another environment; database tests roll back their isolated test schemas.
